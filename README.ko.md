# Drive Integration

[English](README.md) | [한국어](README.ko.md)

**Unreal Engine 5.6과 C++ 서버를 연결해 차량 주행, 상태 동기화, 디버깅을 구현한 개인 프로젝트입니다.**

## 1. 프로젝트 소개

운전 입력을 서버에서 계산하고 그 결과를 Unreal 화면에 반영하는 Windows용 운전 시뮬레이션입니다. 차량이 움직이는 기능에 더해, **데이터가 어떤 경로로 전달되고 문제가 생겼을 때 어떻게 확인할 수 있는지**에 중점을 두었습니다.

회사에서 담당한 **패킷 송수신·직렬화와 전체 소프트웨어 구조 설계** 경험을 바탕으로 구성했습니다. 충돌과 통신 상태를 확인하는 **디버그 화면은 이번 개인 프로젝트에서 추가한 작업**입니다.

### 현재 실행해서 확인할 수 있는 내용

| 영역 | 구현 내용 |
|---|---|
| 차량 주행 | 세단·경차·트럭·오토바이 선택, 가속·제동·조향·후진, 지면 접촉과 충돌 |
| 도심 주행 | 신호가 있는 도로, NPC 차량과 보행자, 장애물 우회와 사고 반응 |
| 차량 설정 | 파일로 관리하는 차종·부품 데이터, 정차 중 부품 선택·적용 화면. 비교용 부품 조합은 현재 세단 중심 |
| 확인 도구 | 속도·연결 상태 HUD, 충돌·바퀴 접지 디버그, 주행 기록·재생 |

**현재 범위:** 같은 PC에서 클라이언트와 서버를 실행하는 개발용 프로젝트입니다. 차량 물리와 NPC 행동은 간소화 모델이며, 실차 정밀 시뮬레이터나 온라인 멀티플레이 게임으로 완성된 상태는 아닙니다. 차체 변형은 화면 효과이며 서버 충돌체를 바꾸지는 않습니다. 실시간 지면·장애물 측정은 실험 모드로 제공하며, 최신 빌드의 주행 감각·화면·장시간 실행 확인은 남아 있습니다.

## 2. 직접 구현한 부분

### 패킷 송수신과 데이터 처리

**WebSocket은 데이터를 주고받는 연결**, **Protobuf는 데이터를 바이트로 표현하는 규격**입니다. [vehicle.proto](protocol/vehicle.proto)에 메시지 형식을 정의하고, 입력을 보내는 시점부터 수신 결과를 차량에 적용하기까지의 처리를 구현했습니다.

1. **연결 확인 — `Hello`**

   연결 시 메시지 버전과 지원 기능을 확인해, 서로 호환되는 클라이언트와 서버인지 검사합니다. 소켓 연결만으로는 서로 같은 메시지 형식을 사용하는지 알 수 없기 때문입니다. 예를 들어 `vehicle-loadout.v1`은 차량 부품 조합 기능을 지원한다는 표시입니다. 필요한 규격·기능이 맞지 않으면 주행을 시작하지 않습니다.

2. **입력 전송 — `ControlCommand`**

   가속·제동·조향 값을 전송 가능한 바이트로 바꾸어 보냅니다. 이 과정을 **직렬화**라고 합니다. 서버는 바이트를 다시 값으로 읽는 **역직렬화**를 수행하고, 입력의 유효성과 현재 주행을 제어할 권한을 확인합니다.

3. **계산 결과 전송 — `WorldState`**

   서버가 위치·속도·바퀴 상태 등을 계산해 주기적으로 보냅니다. 입력마다 응답 하나를 기다리는 구조가 아니라, 계속 갱신되는 차량 상태를 화면에 반영하는 구조입니다.

4. **Unreal 객체에 반영**

   나뉘어 도착한 수신 조각을 하나의 메시지로 모으고 크기·주행 식별자·순번을 검사합니다. 유효한 상태만 게임 스레드에서 차량과 HUD에 적용해, 이전 주행의 데이터가 현재 차량을 덮어쓰지 않도록 했습니다.

`Hello`는 이 프로젝트에서 정의한 초기 확인 메시지이며 로그인 인증은 아닙니다. 서버는 Protobuf 생성 코드를 사용하고, Unreal에서는 필요한 Protobuf 형식의 읽기·쓰기를 구현했습니다.

코드: [메시지 직렬화](unreal/DriveIntegration/Source/DriveIntegration/SimCoreProtocol.cpp) · [클라이언트 연결·수신](unreal/DriveIntegration/Source/DriveIntegration/SimCoreClientComponent.cpp) · [서버 송수신](cpp/host/src/websocket/ws_server.cpp)

### 연결 상태와 주행 상태 관리

연결이 잠시 끊기는 상황과 새로운 주행을 시작하는 상황을 구분했습니다. **같은 Play에서 재접속하면 기존 주행을 유지하고, 새 Play에서는 초기화**합니다. 이미 처리했거나 더 오래된 상태는 순번으로 걸러냅니다.

또한 서버에는 **송신 중인 상태와 최신 대기 상태 하나만** 남깁니다. 전송이 밀릴 때 과거 상태를 계속 쌓지 않도록, 아직 보내지 않은 상태를 최신 것으로 교체합니다. Unreal은 최신 상태와 짧은 시간의 움직임 예측을 사용해 화면을 표시합니다.

### 차량 설정을 코드와 분리

차종별 무게·크기·바퀴 등 설정을 JSON 파일로 관리하고, 엔진·타이어·서스펜션 같은 부품을 ID로 선택하도록 구성했습니다. 같은 차종에서도 부품을 바꾸어 계산에 사용할 값을 변경할 수 있습니다.

서버와 Unreal이 같은 설정을 사용하는지 확인하고, 호환되지 않는 조합은 적용 전에 검사합니다. 현재 부품 교체가 차량 총질량을 자동으로 다시 계산하는 단계까지 구현된 것은 아닙니다.

코드·데이터: [차량 설정](cpp/host/config/vehicles/catalog.json) · [Unreal 설정 읽기](unreal/DriveIntegration/Source/DriveIntegration/SimCoreVehicleCatalog.cpp) · [부품 구조와 적용 범위](docs/architecture.md)

## 3. 구조와 실행 방법

### 실제 실행 화면

![Signal City에서 플레이어 차량·NPC와 한국어 HUD가 표시된 실제 실행 화면](docs/images/signal-city-runtime-20261030.png)

*2026-10-30 촬영. Unreal Engine 5.6의 게임 실행 창에서 로컬 C++ 서버에 연결한 화면입니다. 플레이어 차량, NPC 차량, 도심 도로와 HUD의 정상 연결 표시를 확인할 수 있습니다. 기본 파일 기반 모드, 1600×900 원본입니다.*

### 전체 구성

![Unreal의 입력·화면 표시와 C++ 서버의 계산을 분리한 구조](docs/images/system-overview.svg)

*기본 실행 구조를 설명하는 구성도입니다.*

| 구성 | 담당 역할 |
|---|---|
| Unreal 클라이언트 | 입력 수집, 서버 상태 수신, 차량·카메라·HUD·소리 표시 |
| C++ SimCore 서버 | 입력 검증, 차량·교통 계산, 최종 상태 전송 |
| 공통 데이터 | 통신 규격, 차량·부품 설정, 서버용 지면·도로·신호 정보 |

차량의 최종 위치와 움직임은 서버가 결정합니다. 계산과 화면 표시를 나눠, 주행 문제가 발생했을 때 서버 계산·통신·표시 중 어느 부분을 확인해야 하는지 추적할 수 있도록 했습니다.

서버는 기본 **60Hz, 즉 1초에 60번** 계산합니다. 화면을 그리는 횟수(FPS)와는 별개입니다. 기본 실행에서는 Unreal에서 내보낸 지면·교통 파일을 서버가 읽으며, 이 묶음을 코드에서 `MapPackage`라고 부릅니다.

### Windows에서 실행

환경: Windows 64-bit, Unreal Engine 5.6, Visual Studio 2022(C++ 데스크톱 개발), CMake 3.21 이상, Git, PowerShell.

저장소 루트에서 서버를 준비하고 실행합니다.

```powershell
.\cpp\host\scripts\setup.ps1
.\cpp\host\scripts\build.ps1
.\scripts\run_signal_city_server.ps1 -Background
```

1. `unreal\DriveIntegration\DriveIntegration.uproject`를 열고, 필요하면 C++ 모듈을 빌드합니다.
2. `/Game/SignalCity/Maps/L_SignalCity`에서 **Play**를 누릅니다.
3. HUD의 **정상 연결** 표시를 확인하고 주행합니다. 기본 실행 전에 맵을 다시 Bake할 필요는 없습니다.

| 조작 | 키 |
|---|---|
| 가속·제동·정지 후 후진 / 조향 | `W/S` / `A/D` |
| 사이드 브레이크 / 차종 선택 | `Space` / `1–4` |
| 부품 선택 / 디버그 표시 | `G` / `F3` |
| 시각 기록 시작·종료 / 재생 | `R` / `F6` |

게임 HUD와 부품 선택 화면은 한국어입니다. 서버는 `ws://127.0.0.1:9000/`에서 하나만 실행합니다. 종료하려면 실행기가 표시한 PID로 `Stop-Process -Id <PID>`를 사용합니다. 로그는 `runtime_logs/`에 저장됩니다.

[맵 실행 안내](docs/guides/signal_city_quickstart.md) · [Windows 배포 안내](docs/guides/windows_package.md)

## 4. 문제 해결과 검증

### 입력 반응이 점점 늦어지는 문제

화면 FPS가 충분해도 과거 상태가 쌓여 있으면 차량은 늦게 반응할 수 있습니다. 서버의 송신 대기를 최신 상태로 교체하도록 제한하고, 클라이언트도 오래된 순번을 다시 적용하지 않도록 했습니다.

확인할 때는 FPS와 함께 **상태 수신 간격과 마지막 수신 이후 지난 시간**을 봅니다. 수신 간격은 네트워크 왕복 시간(RTT)이 아니며, 최신 상태로 교체하면서 생긴 순번 공백을 패킷 유실로 단정하지 않습니다. 실제 키 입력부터 화면 반응까지의 시간은 [별도 측정 절차](docs/guides/input_latency_measurement.md)로 구분합니다.

### 재접속 때 차량이 사라지거나 초기화되는 문제

일시적인 수신 지연, 연결 복구, 새 주행 시작을 구분하고, 같은 Play의 재접속에서는 위치와 사고 상태를 유지하도록 했습니다. 잠깐 수신이 늦었다고 차량을 삭제하거나 출발점으로 초기화하지 않습니다.

2026-10-04 실제 서버 통신 검사에서는 **같은 Play 복구와 새 Play 초기화**를 확인했습니다. 별도의 실시간 지면 시험에서는 응답 3개를 누락시킨 뒤 같은 연결에서 계산이 재개되고 NPC·보행자 18개가 유지되는 것을 확인했습니다.

### 눈으로 확인하고, 같은 조건으로 다시 검사하기

**F3 디버그 화면**에는 충돌 박스, 바퀴 접촉 위치, 지면 방향, 하중과 미끄러짐을 표시했습니다. 차가 떠 보이거나 파묻힐 때 화면의 모양과 계산에 사용한 접촉 정보를 비교할 수 있습니다.

![차량 충돌 박스·바퀴 하중·미끄러짐과 서버 연결 상태를 보여주는 실제 F3 디버그 화면](docs/images/signal-city-debug-20261030.png)

*2026-10-30 같은 실행에서 F3를 켜고 촬영했습니다. 청록색 박스는 충돌 범위, 초록색 바퀴 표시는 하중·미끄러짐, 분홍색 표시는 충돌 피해 정보입니다. 왼쪽 위에는 연결 상태와 상태 수신 주기·순번 등이 표시됩니다.*

**시각 재생**은 받은 상태를 다시 표시해 문제 장면을 확인하는 기능입니다. **서버 물리 재생**은 기록한 입력과 필요한 측정값으로 다시 계산해 위치·방향 결과를 비교합니다. 코드 수정 뒤에도 같은 조건에서 결과가 유지되는지 확인하기 위한 용도입니다.

| 검사 날짜 | 확인한 결과 |
|---|---|
| 2026-10-04 | 서버 CTest **62/62**, Unreal 자동 검사 **138/138** 통과. Unreal 결과에는 기존 경고 7개 포함 |
| 2026-10-04 | 실시간 측정 기록 **2,400프레임** 재계산에서 위치·방향 오차 0. 해당 기록과 실행 조건에 한정한 결과 |
| 2026-10-22 | 한국어 HUD·부품 선택·상태 표시·재생 관련 자동 검사 **42/42** 통과 |

위 표는 기록된 검사 결과이며, README를 수정하면서 새로 실행한 결과는 아닙니다. Unreal 자동 검사는 화면을 그리지 않는 **NullRHI** 환경에서 진행했으므로, 실제 화면 품질·운전 감각·장시간 안정성을 모두 확인했다는 뜻은 아닙니다.
