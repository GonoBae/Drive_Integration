# 2026-08-31 작업일지

## 요청·범위

사용자는 현재 미완료 우선순위 작업 진행과 배경 제작 방법 검토를 요청했다. 오늘은
M3의 authoritative Health/SafeStop HUD, 지면·정적 marker 자동 QA와 배경 제작안을
진행했다. 기존 dirty worktree, `Content/NewMap.umap`, 실제 Landscape package는
보존했다. **commit/push·외부 에셋 구매·배경 맵 교체는 하지 않았다.**

## 구현

### Health와 HUD

- `WorldState.health` field 2, `Health.has_control_command` field 5를 additive로 추가했다.
  schema v2와 기존 필드 번호는 유지하고 Hello에 선택 `world-health.v1`을 알린다.
- 서버가 실제 적용한 상태를 `awaiting_reset`, `awaiting_control`, `active`,
  `safe_stop`, `reconnect_required`, `estop_latched`로 발행한다. tick overrun 누적,
  마지막 승인 command age·존재 여부와 고정 reason을 함께 보낸다.
- 별도 Health frame을 추가하지 않는다. 차량 상태와 동일 latest-wins queue slot,
  sequence, map/play identity에 넣어 상태/Health 대체와 가짜 sequence 누락을 피한다.
- 초기화·reset·reconnect는 command 없음/age=0으로 표시한다. EStop을 최우선으로
  표시하며 기존 process-lifetime latch와 제어·물리 정책은 변경하지 않았다.
- Unreal은 누락·unknown·잘못된 값·100ms stale·연결/Hello/map 실패를 정상 Active로
  표시하지 않는다. 숫자는 기존 경량 HUD 주기로 갱신하되 safety label 변화는 다음
  tick에서 갱신한다. Health 표시가 fresh control 송신을 막지 않는다.
- 새 PIE 이전에 EStop이 이미 걸려 Reset이 거부되면 play ID가 다르다는 이유로 정지
  원인이 숨겨지는 경로도 보완했다. 현재 연결 generation·Hello·map·증가 sequence로
  확인한 **전역 EStop 진단만** 읽고, 다른 play의 pose·Active는 채택하지 않는다.
- Python binding도 단일 proto 원본에서 재생성했다. Python relay runtime은 계속
  기본 OFF이며 이 작업으로 수동운전 경로에 다시 추가하지 않았다.

### Unreal 지면·marker QA

- 별도 transient world의 실제 `WorldStatic` collision ray로 높이·법선,
  Asphalt/LowFriction/Rough와 actor/component tag·Physical Surface 우선순위를 검사한다.
- Ground Actor filtering, 위쪽 장애물 무시, 경사 normal의 ENU 변환, spawn coverage,
  sample budget과 잘못된 설정의 fail-close를 검사한다.
- 기존 static CSV 직렬화를 작은 `SimCoreStaticCollisionSnapshot::BuildCsv` wrapper로
  공용화했다. 실제 marker actor의 좌표/scale/yaw, ID 정렬·중복 거부, 비활성 marker
  제외와 yaw-only OBB 제약을 검사한다. Bake 동작은 바꾸지 않았다.
- 자동 테스트가 `Saved/Automation/SimCoreGroundQa/<GUID>`에 40×40m, 41×41 lattice,
  `SIMGHF2` 저마찰 지면과 marker 2개의 별도 package를 남긴다. 서버 로더 연동 시험에
  사용할 수 있으며 사용자 맵이나 실제 package를 대체하지 않는다.

### 검증 도구 안전성

`scripts/smoke_health.py`는 전용 child 서버를 임시 localhost port에 실행해 실제
WebSocket Hello→Reset→Active→SafeStop→복구→hard timeout→같은 PIE 재연결→EStop을
검사한다. `--source-id`에 실행별 무작위 identity를 넣고 최초 server Hello와 모든 state에서
일치 여부를 검사한다. free-port 확보/실행 사이에 다른 서버가 해당 port를 차지해도
그 서버에는 Reset/EStop 등 application frame을 보내지 않는다. 종료 대상도 직접 생성한
child process로 한정한다. 1008 reason·hard deadline과 EStop 유지 관찰 구간도 검증한다.

  LaneGraph는 구현하지 않았다.

  bootstrap 기본값은 유지한다. demo entity는 새 코스에서 끈다.
- 새 launcher는 시작한 PID의 listener를 확인하고, port 충돌 시 기존 프로세스를

겹침 길이를 수정했다. 반경 19.5m를 0.25° 간격으로 검사하는 UE 회귀 테스트와 실제

## 사용자 주행 피드백 후속 — 조향·카메라·세단 외형

위 코스 구현 인계 뒤 사용자가 실제 운전에서 ① 뻑뻑한 코너링 ② 회전 불가능한
카메라 ③ 블록형 차량을 지적했다. 세 작업을 독립적으로 구현하고 Pawn 통합/빌드/
실제 렌더는 순차 검증했다. [사용법·설정·한계](../vehicle_driving_refinement.md)에
재현 방법을 정리했다.

### 조향

- `vehicle_sedan.cfg`와 내장 기본값의 중앙 조향각 32→35°, rack 증가 1.35→1.80rad/s,
  복귀 1.80→2.20rad/s, 속도별 조향 envelope 5.5→6.8m/s².
- 마찰 계수·tire force·Ackermann·서스펜션·충돌 공식을 변경하지 않았다.
  heading을 강제로 더 회전시키는 표시 보정도 추가하지 않았다.
- 정속 full steering의 CG 반경: 10.8km/h 4.398→3.940m,
  18km/h 5.072→4.414m, 30km/h 13.255→11.375m,
  40km/h 23.948→20.769m, 90km/h 149.489→120.891m.
- 300ms 조향 응답 23.6→31.3°, 저속 full rack 약 417→350ms.
  고속 시험의 실제 횡가속도 5.162m/s², tire slip angle 2.247°,
  sideslip 1.117°, roll 2.636°와 네 바퀴 접지/마찰 원 제약을 확인했다.
- 특정 실차 데이터 동정/검증이 아닌 generic sedan 자체 모델 회귀 수치다.
  사용자 수정본 운전 감각 확인은 남아 있다.

### 자유 회전 외부 카메라

`SimCoreOrbitCamera`와 Pawn 입력 연결을 추가했다. 마우스 orbit, 휠 줌, C 뒤쪽 복귀,
게임패드 오른쪽 스틱/클릭을 지원한다. mouse delta와 gamepad rate를 분리하고
30/60/120/240fps 수학 회귀, config/delegate 실제 바인딩과 offline Pawn을 검사한다.
차체 yaw 기준의 수평 추적, world-space pivot, wall probe/거리 복원이며
차체 pose·ControlCommand를 수정하지 않는다. 4종 카메라 전체/운전석/replay 촬영
완료로 간주하지 않는다. PIE 화면 클릭과 Shift+F1 사용법도 문서화했다.

### 자체 세단 형상·재질

Editor `BuildSedanVisual`은 `/Game/Vehicles/Sedan`에 차체/휠 StaticMesh와 도장·유리·
고무·합금·트림·등화류 등 10종 재질을 생성한다. 외부 모델/bitmap/유료 에셋이나
새 차량 물리 SDK를 도입하지 않았다. 곡면 후드/트렁크·캐빈·유리·휠 아치·미러·손잡이·
그릴·등화류를 추가하고 양쪽 면을 가진 원형 타이어/휠을 네 독립 pivot에 연결했다.
총 39,256 triangles(차체 21,336 + 바퀴 4,480×4), cm 단위와 기존 차축/반지름을 유지한다.

초기 생성에서 Unreal face winding과 면 법선 관계를 바로잡았고 조립 후 40k triangle
예산을 맞췄다. 실제 front/rear 렌더에서 램프의 planar quad가 곡면에 묻히고 범퍼
경계가 맞지 않는 것을 발견해 surface-conforming lamp와 공유 경계/하부 closure로
보완했다. geometry Automation에 면 winding/유한성/휠 공간/예산뿐 아니라 fascia
boundary 일치와 lamp clearance 회귀를 추가했다.

시각 메시는 `NoCollision`, root unit scale이며 차속 rolling·서버 suspension/차체 자세
표시를 보존한다. 저장 메시/재질은 component 참조를 통해 유지하고 생성/QA 코드는
Editor 모듈에 격리한다. Native constructor는 초기 미생성 에셋을 검사한 뒤 로드하고
기존 기본 도형 fallback을 보존한다. 실제 cook 검증은 아직 아니다. 미러 등 장식은
서버 충돌 proxy에 포함하지 않으며 실내·기능성 제동등/방향지시등은 미구현이다.

## 편집 화면 떨림 진단 후속 기록

사용자는 Lit 편집 화면의 도로/지면 떨림이 Unlit에서 멈추고, Lumen diffuse·동적
그림자·그리드를 각각 꺼도 남는다고 보고했다. 최종적으로 `ShowFlag.TemporalAA 0`
적용 뒤 "안떨린다"고 확인했다. 사용자 GIF 관찰과 별도 96장 TSR/FXAA·selection
outline 비교는 [문제 해결 기록](../troubleshooting/ue-editor-temporal-aa-surface-flicker.md)에
정리했다. 별도 비교는 사용자 시점/선택 상태의 완전 재현이나 장기 안정성 시험이 아니다.

효과가 확인된 것은 시간축 AA를 제거한 편집 화면의 우회다. 엔진 버그/특정 geometry를
단독 원인으로 확정하지 않는다. 콘솔 강제값을 `2`로 해제한 뒤 편집 뷰포트의 Temporal AA
체크만 끄는 UI 절차를 기록했으며, 사용자의 UI 저장·재시작 지속 확인은 아직 없다.
제품 `DefaultEngine.ini`의 게임 AA나 맵·물리는 이 진단을 위해 바꾸지 않았다.
또한 사용자 고속 바퀴 회전 피드백은 추가 확인 항목으로 유지하며 해결 완료로 세지 않는다.

### 저작 데이터와 지면 검증

- `SimCoreVirtualCityTrafficLayout`은 QA용 `drive_route.csv`와 별도로 25개 방향성
  lane segment·successor·속도·폭·정지선 group을 정의한다. T 교차로의 본선 양방향
  접근과 지선 접근에 신호 head 3개, phase group 2개를 둔다.
- 반대 직진과 충돌하는 본선 동쪽 진행의 지선 좌회전은 저작하지 않았다. 막다른
  지선 도착 lane은 명시적 terminal이며 임의 U-turn 연결을 만들지 않는다.
- `ExportVirtualCityTraffic`가 기존 저장 맵의 ground component/transform/tag를
  확인하고 실제 WorldStatic asphalt 충돌을 중심·양쪽 반폭·1m 간격으로 측정했다.
  맵 생성/저장이나 지면 재Bake 없이 `traffic_network.json`만 최초 생성했다.
- 결과는 lane 25개/head 3개, source collision `fnv1a64:17293781b645eac0`,
  traffic 파일 byte checksum `fnv1a64:b8e840af96a68990`다.
- C++ loader는 strict JSON 타입·필드·ID·예산·topology·정지선/head 관계와 실제
  MapPackage `GroundQuery`의 중심/폭 지면·높이를 다시 검증한다. JSON type을
  보존하는 shape 검증을 Boost property_tree 파싱 앞에 두었다. 새 의존성은
  `boost-property-tree`이며 외부 차량 물리 SDK를 추가하지 않았다.
- `.gitattributes`에 traffic JSON의 `-text`를 추가해 checkout 줄바꿈 변환으로
  파일 byte checksum이 달라지지 않게 했다.

### 서버 권한·원자 통신·복구

기존 목표 문서의 Unreal SignalController 시간 권한을 서버 simulation clock으로
정리하고 [ADR-014](../decisions/ADR-014-server-clock-traffic-signals.md)에 이유를 남겼다.
차량/신호 reset과 기록 시간을 일치시키는 구현 결정이며 별도의 사용자 승인으로
꾸며 기록하지 않았다. Unreal은 도로 저작·실제 지면 측정과 신호 표시를 맡는다.

- 30초 cycle: 전부 적색 2초 → 본선 녹색 12초/황색 3초 → 전부 적색 2초 →
  지선 녹색 8초/황색 3초. countdown은 해당 head의 다음 색 변경까지 시간이다.
- schema v2에 선택 `traffic-signals.v1`, 신호 목록/network checksum을 더했다.
  차량 pose·Health·신호를 한 WorldState와 같은 sequence/map/play identity로 보낸다.
  C++ serializer, Unreal 수동 wire parser와 Python 생성 binding을 함께 갱신했다.
- 새 PIE는 0초/all-red로 시작하며 같은 PIE 재연결은 simulation 시간을 유지한다.
  control 비활성·SafeStop·hard timeout·EStop 또는 map identity 불일치에는 all-red다.
- cfg 선택 키 `traffic_network`/CLI override를 추가했다. 기존 cfg는 계속 호환한다.
  250ms watcher의 파일/지면 검증은 physics thread 밖에서 수행하고 immutable
  candidate를 tick 경계에서 활성 map과 대조해 적용한다.
- 읽기 실패 시 signature를 성공 처리하지 않는다. 일시적인 공유/교체 오류는 같은
  파일 signature라도 250ms~5초 backoff로 재시도하고 동일 오류 로그는 반복하지 않는다.
  무효 traffic 후보는 보존한 유효 객체를 대체하지 않는다.
- Ground Bake로 collision identity가 바뀌면 기존 head는 적색이 된다. 수동운전을
  영구 차단하거나 서버 재시작을 요구하지 않는다. 기존 지면 hot reload 자체의
  socket fence·자동 재연결·새 PlaySession reset 절차는 유지한다.

### Unreal 표시·최종 검토 보완

게임 world에서만 transient 신호 actor 3개를 생성한다. 기둥·head·세 색 렌즈는
`NoCollision`이며 차량 접근 방향을 향한다. 기존 Hello/map/세대/play/sequence gate를
통과한 snapshot만 설치하고 연결 종료/오류/unknown/stale에는 녹색을 유지하지 않는다.
100ms freshness는 게임스레드 수신 처리 시각 기준이며 종단 지연 상한이나 pause/hitch
중의 hard-real-time 표시 보장은 아니다.

최종 독립 검토에서 허용 double heading `359.999999`가 float wire field의 `360`으로
반올림되어 Unreal이 WorldState 전체를 거부할 수 있음을 발견했다. 변환 결과만
동일 방향 `0`으로 wrap하고 0/90/359.999/359.999999와 무효 360/음수 회귀를 추가했다.
현재 세 head의 90/270/180도에는 나타나지 않았지만 허용 입력 계약의 결함으로 고쳤다.
시험의 `FLinearColor` 초기화 경고도 제거했다.

본선의 새 정지선 페인트는 아직 없다. 이번 정지선은 graph lane 끝의 제어 metadata다.
기존 지선 정지선은 보존했으며 exporter 로그와 안내도 이 차이를 명확히 했다.

## 2차 조향 피드백 — 조금만 빨라도 회전이 부족함

이 절은 속도 cap을 8.5로 완화했던 중간 이력이다. 이후 아래의
“속도 독립 조향 구조 수정”에서 cap 자체를 제거했으므로 현재 동작·합격기준이 아니다.

사용자가 신호 기반 인계 후 "속도가 조금만 빨라도 회전이 너무 안돼"라고 보고했다.
불편한 정확한 계기판 속도는 질문했으나 아직 답변 전이므로 도심 20~50km/h를
우선 비교했다. [현재 설정·비교·한계](../vehicle_driving_refinement.md)를 갱신했다.

### 원인과 변경

최근 사용자 주행 로그에서 steering ±1이 정상 도착했고 서버 적용 지연은 약
5~7ms였다. Unreal 입력→부호 변환→wire와 wheel 표시에는 추가 속도 감쇠가 없었다.
반면 서버의 6.8m/s² 조향 요청 상한은 약 18.4km/h부터 적용되어 30km/h에서
약 14.7°, 40km/h에서 약 8.45°만 허용했다. rack 속도를 다시 높이는 것보다
정상 선회 조향 제한을 조정하는 것이 이번 증상에 직접적이었다.

6.8/8.0/8.5/9.0 후보를 오프라인으로 비교한 뒤 **8.5m/s²**를 선택했다.
`vehicle_sedan.cfg`와 `VehicleParameters` 기본값만 함께 바꿨다. 타이어 mu/강성·
마찰 원·서스펜션·질량·yaw 적분/충돌·35° 최대 lock·1.8/2.2 rack rate는 유지했다.
Unreal 입력이나 화면만의 회전 배율을 추가하지 않았다.

### 측정과 회귀

이전 반경 지표는 종방향 speed/body-Z yaw_rate의 비율이었다. 이번에는 ENU 위치
증분의 진행 방향 변화와 chord 길이에서 실제 CG 궤적 반경을 계산했다. 이전
문서의 지표는 이력으로 남기되 엄밀한 궤적 반경이 아니었음을 정정했다.
pedal-only controller의 정속 안정화를 보강하고 3초 구간 속도 평균/범위와
좌우 실제 곡률을 기록한다. 위치·속도를 덮어쓰지 않는다.

| 목표 | 기존 반경(6.8) | 수정 반경(8.5) | 수정본 실측 종방향 속도 |
|---|---:|---:|---|
| 30km/h | 11.432m | 10.092m | 평균 30.428km/h, 범위 약 30.299~30.511km/h |
| 40km/h | 20.797m | 17.316m | 약 40.000km/h |
| 50km/h | 33.356m | 28.244m | 약 50.000km/h |
| 90km/h | 121.005m | 109.303m | 약 90.001km/h |

20km/h full-lock 후보는 평균 19.278km/h로 목표 속도를 유지하지 못했다.
정속 검사의 허용오차를 넓혀 통과시키지 않고 해당 목표를 엄격한 비교에서 제외했다.
10.8/18km/h 저속 회귀는 유지했다. 따라서 20km/h 후보에서 반경이 작아진 전부를
조향 개선으로 주장하지 않는다. 30/40/50km/h의 비교는 평균 속도 오차 0.20m/s 이내,
기존 대비 반경 10% 이상 감소를 검사한다.

좌우 방향/반경 2% 이내 대칭·네 바퀴 접지, 90km/h 양방향 body slip<3°·tire slip<4°·
roll<8°, 표본 속도 범위<0.50m/s를 검사했다. 수정본 90km/h 좌회전 최대값은
body slip 1.324°/tire slip 2.824°/roll 2.944°다. 별도 지면 friction 배율0.35에서도
양방향 선회 시 원래 surface-scaled mu×Fz 마찰 원을 넘지 않았다. 기존 full throttle
traction·후진·중립 복귀·경사/충돌 회귀도 유지한다.

- C++ Release `ALL_BUILD` 성공. 최종 추가 시험까지 CTest **16/16**, 4.15s, skip0.
- `vehicle_physics_tests.exe --steering-sweep`는 후보를 메모리에서만 비교하는 진단 모드다.
- 격리 실제 Health WebSocket smoke **PASS**:
  `runtime_logs/health-smoke-20260831-165128-961487e6.*.log`.

작은 코너를 저속처럼 돌도록 만들지는 않았으므로 여전히 감속이 필요하다. 이번
자동 회귀는 특정 실차 계측 검증·사용자 조작감·1080p/30분 인수의 대체가 아니다.
일정에 품질 수정 실적과 사용자 인수 대기를 남겼고 관리 목표/버퍼는 유지한다.
commit/push는 하지 않았다.

## 속도 독립 조향 구조 수정 — 입력·기구와 타이어 물리 분리

### 요청과 판단 정정

사용자는 같은 조향 입력인데 속도가 오르면 바퀴가 덜 꺾이는 점을 지적했고,
다음 작업으로 제안한 조향 구조 수정과 기본 주행 재검증을 승인했다.
기존 `atan(wheelbase × comfortable_lateral_accel / speed²)` 제한은 타이어가
만들어낸 물리적 언더스티어가 아니라 입력 보조였다. 6.8→8.5 수치 조정만으로는
고정 조향 입력 계약을 만족하지 못했음을 명확히 정정한다.

이번 범위는 조향 구조·시험·문서·테스트 서버 적용이다. NPC와 보행자,
SensorRig·기록/재생·패키징까지 동시에 구현한 것은 아니다.

### 구현

- 목표 중앙 조향각을 속도와 무관한 `clamp(steering, -1, 1) × 최대각`으로 바꿨다.
  최대 중앙각 35°, rack 증가 1.80rad/s·복귀 2.20rad/s는 유지한다.
- 좌우 앞바퀴는 별도 Ackermann 각도를 유지한다. 중앙각은 어느 한 바퀴의 실제
  각도와 같다는 뜻이 아니다. 지면 coverage 안전정지 분기에서 두 앞바퀴 각도를
  중앙각으로 덮던 작은 불일치도 같은 계약에 맞춰 수정했다.
- `comfortable_lateral_accel_mps2`를 파라미터·validation·loader·cfg에서 제거했다.
  strict 차량 설정은 v6이며 v5는 항목 삭제·버전 전환을 명시하는 오류로 거부한다.
  v6에 옛 항목이 있어도 unknown key로 거부하고, 버전은 정확한 정수 토큰을 요구한다.
  별도의 선택형 속도 보조는 이번에 추가하지 않았다.
- 타이어 강성·mu·마찰 원·하중·서스펜션·yaw 적분·traction control은 바꾸지 않았다.
  외부 물리 SDK를 도입하거나 화면 회전/yaw를 증폭하지 않았다.
- UE 정상 입력/직렬화/개별 휠 표시에는 추가 속도 감쇠가 없었다. UE 제품 코드는
  변경하지 않고 `SimCoreSteeringContractTests.cpp`에 독립 계약 시험 2개를 추가했다.

### 자동 시험과 측정

실제 pedal 입력으로 진입 속도 0/3/10/25/-5m/s를 만든 뒤 같은 명령 이력
`1, .25, 0, -1, .5, 0`을 적용했다. 정지 차량과 매 tick 중앙각·개별 휠각 차이가
1e-6rad 이내이고 유한 응답·복귀·방향 전환·Ackermann을 유지한다. 90km/h 진입에서도
0.35초 이내 중앙 35°에 도달할 때 종방향 속도는 여전히 20m/s보다 크다.
과대 입력 ±2 clamp와 유한 지면 안전정지의 Ackermann 유지도 검사한다.

정속 측정은 throttle/brake만 조절하며 pose·속도·yaw를 덮지 않는다. ENU 위치 증분의
진행 방향 변화와 chord 길이로 CG 경로 반경을 구하고, 목표 종방향 속도·실측
종방향 속도·ENU 경로 속도를 구분한다.

|---:|---:|---:|---:|---:|---:|
| 1 | 10.8km/h | 10.7999km/h | 11.4880km/h | 35° | 4.1891m |
| 1 | 18km/h | 18.0001km/h | 18.8149km/h | 35° | 4.4839m |
| .15 | 30km/h | 30.0000km/h | 30.0181km/h | 5.25° | 30.4765m |

좌우 경로 곡률 부호와 반경 2% 대칭, 네 바퀴 접지, roll<8°를 확인했다. 위 정속
케이스는 종방향 평균 목표 오차<0.20m/s·표본 속도 폭<0.50m/s를 지켜야 한다.
선회 권한이 사라져도 통과하지 않도록 해당 저속/작은 고정각 케이스의 반경은
기하 CG 반경의 0.85~1.5배 범위도 검사한다(저속 full-lock은 더 좁은 별도 범위).
이 범위를 고속 full-lock 시험에 적용하지 않는다.

별도의 90km/h full-lock 양방향 시험은 Neutral·무구동 3초 동안 중앙 ±35°를
유지한다. 종방향 속도는 90.014→61.928km/h, 최대 tire slip은 43.878°,
마찰 원 최대 이용률은 1.0이었다. 매 tick 힘이 mu×Fz 예산을 지키고 pose가 유한하며,
평면 운동+몸체 yaw 에너지가 초기값의 1.05배를 넘지 않는다. 따라서 물리 한계에서는
각도를 몰래 줄이지 않고 포화·미끄러짐·감속이 생긴다. 이는 특정 실차의 고속 급조향
거동을 계측 검증했다는 뜻이 아니다.

`--steering-sweep`는 이제 cap 후보 비교가 아니라 입력 .04/.15/1을 각각 고정하고
여러 목표 속도에서 `longitudinal_kph`와 `path_kph`를 함께 출력하는 진단이다.
full-lock 상태의 목표 30/40/50km/h는 실제 종방향 약19.278km/h·경로 약20.039km/h로
감속하므로, 반경4.644m를 “30~50km/h의 선회 반경”으로 보고하지 않는다.
저마찰 지면 배율0.35에서도 원래 surface-scaled 마찰 원을 유지한다.

## 후속 직접 재현 — 지지력 누락·조향 표시 수정과 v7 균형 조정

사용자가 다시 속도별 회전 차이를 지적하고 직접 시험할 것을 요청했다. 바퀴 각도와
차체 선회 중 무엇인지 사용자에게 재진단을 맡기지 않고, 실제 물리 입력 시험과 실제
Unreal Pawn 표시 시험으로 경로를 나눠 확인했다. 아래는 앞의 v6 결과 이후 기록이다.

### 재현과 확인된 원인

- `vehicle_cornering_probe`를 추가했다. 실제 `VehiclePhysics`에 throttle/brake/gear/steer만
  넣고 고정 60Hz로 실행한다. pose·속도·yaw를 직접 주입하지 않는다. 무한 평지를 써서
  유한 도심 맵 경계와 타이어 문제를 분리했고, 최고속도 50m/s에 실제 도달했는지도 검사한다.
- 3개 앞/뒤 강성 후보 × 7개 진입 속도(10.8/18/30/40/50/90/180km/h) ×
  정속 입력 3종 및 Drive-full/Drive-coast/Neutral 좌우 전타각 조합,
  총 **189개 시나리오·441행**을 측정했다. 정속은 선회 20초 끝의 3초 평균,
  과도 시험은 매 초의 마지막 0.5초 평균이다. heading_change만 입력 이후 누적이다.
  peak·min도 해당 표본 구간의 값이지 전체 과도 구간 극값은 아니다.
- 0.015 입력은 중앙 0.525°의 작은 신호 식별용이다. UE 입력 deadzone 0.02보다
  작으므로 실제 키보드/Pawn 입력 시험이라고 주장하지 않는다. ±1 전타각은 별도 검사한다.
- 중앙각 35°, 개별 앞바퀴 약41.368°/30.163°는 최고속에서도 유지됐다.
  하지만 접지가 없으면 `ExternalVehiclePawn::Tick`이 pivot rotation 갱신까지 건너뛰어
  이전 조향을 표시하는 버그가 있었다. 독립 fixture로 기존 코드가 실패함을 확인했다.
- 물리에서는 압축 한계의 실제 속도 제약 반력을 타이어 하중에 넣지 않았다.
  50km/h·입력0.15·55k/55k 정속에서 spring/damper **13,422.96287N**,
  바깥 앞바퀴 hard-stop **21.4502003Ns**였다. `spring + J/(1/60)`은
  **14,709.97489N**, 즉 차량 중량과 사실상 동일하다. 마찰 계산에서는 J를 빠뜨려
  약1,287N의 지지력이 누락돼 있었다. 새 force-balance 회귀도 수정 전 실패했다.

### 채택한 수정

1. heave·attitude 뒤의 두 접촉 resolver와 재조회에서 실제 최종 wheel impulse를 tick별로
   합산한다. 위치 보정량이나 solver 반복 중간 impulse 절댓값을 합산하지 않는다.
2. 직전 accepted tick의 `J / producing dt`를 다음 tick의 해당 타이어 하중에만 더한다.
   fresh contact가 있고 법선 방향 압축 한계 clearance≤0.1mm일 때만 사용한다.
   이미 반영한 impulse를 차체 heave·roll·pitch 힘에 다시 더하지 않는다.
   spring force 상한으로 rigid-stop 반력까지 잘라내지 않는다.
3. reset·환경 교체·접촉 상실·압축 한계 해제·coverage rollback에서는 반력 캐시를 버린다.
   이 결합은 1tick 명시적 추정이며 동시 풀림의 완전한 6DoF 솔버는 아니다.
4. 앞/뒤 고정 per-tire 코너링 강성을 분리하고 기본값과 tracked cfg를 각각
   **60,000/50,000N/rad**로 맞췄다. 앞 하중55% 차량의 작은-slip 언더스티어를
   완화하는 선택이다. 중앙각·rack·mu·마찰원·traction control은 유지했다.
5. cfg **v7**: 기존 단일 `tire_corner_stiffness_n_rad`를 앞/뒤 필드로 나누며,
   v6 migration은 원래 per-tire 값을 양쪽에 복사한다. v5는 speed-cap 항목도 삭제한다.
   버전·누락·중복·unknown·비정상 수치는 strict reject하며 자동으로 덮지 않는다.
6. UE 비접지 pivot은 중심 위치를 유지하면서 최신 조향각을 차체 Up 기준으로 적용한다.
   stale-state 정책·서버 물리·바퀴 rolling 속도·맵/에셋은 바꾸지 않는다.

### 실측과 해석

반경은 ENU 위치 증분과 진행 방향 변화로 구한 실제 CG 궤적이다.
아래는 동일 입력·같은 실제 종방향 속도의 비교이며, 감속으로 작아진 반경을
같은 속도의 개선으로 계산하지 않는다.

| 실제 종방향 속도 | 중앙각 | v6 55k/55k·반력 누락 반경 | v7 60k/50k·반력 포함 반경 |
|---|---:|---:|---:|
| 30km/h | 5.25° | 30.4765m | 29.5373m |
| 40km/h | 5.25° | 31.2917m | 29.6222m |
| 50km/h | 5.25° | 33.9474m | 32.4800m |
| 약90km/h | 1.4° | 145.3770m | 114.520m |

90km/h 최종 CTest 표본은 종방향90.0007km/h, ENU 궤적90.0264km/h다.
0.525°의 작은 신호 회귀는 30/90km/h 반경295.610/303.179m와 독립적으로 유도한
`K=m/L×(b/Cfront_axle−a/Crear_axle)=0.000125rad/(m/s²)`에 2% 이내로 맞는지
검사한다. 그 K는 약0.070235°/g이며 고속 전타각의 포화 영역에는 적용하지 않는다.

50km/h 최종 probe는 spring13,331.78327N+직전 stop1,378.19186N=
14,709.97514N으로 지지력을 복원했다. 반력 수정만으로 50km/h 반경이 크게 줄지는
않았다. 이때 바깥 앞바퀴는 비포화이고 안쪽 앞바퀴가 포화였기 때문이다.
따라서 강성 균형과 반력 수정의 효과를 혼동하지 않는다.

최고속180km/h 전타각에서는 중앙35°를 유지하지만 큰 slip·감속·yaw 과도진동이 남는다.
최종 Drive-full의 1.5~2.0초 표본에서 navigation yaw rate는 약−9.659°/s로,
입력 방향 반대의 과도 구간도 있다. 이 상태를 실차 수준 완료 또는 모든 속도의
회전 문제 해결로 보고하지 않는다. 파라미터/모델의 극한 응답 검증은 P0 잔여다.

### 미채택 실험

안쪽 바퀴의 낮은 Fz에서도 고정 강성 C가 유지되어 일찍 포화하는 문제를 분리하려고
`C=Cnominal×Fz/(m*g*axle_static_share/2)` 선형 하중 의존 후보를 시험했다.
평지 시험 일부는 개선됐지만 기존 `landscape_local_v1`에서 10초 full throttle·
zero steering 회귀가 **max roll65.681°>45°**로 실패했다. 원인을 수치 불안정 또는
지형 경로 변화 중 하나로 단정하지 않았고, 후보식·해당 기대 시험만 제외했다.

## 최고속 과도 추가 진단 / 이번 턴 후속 — 수치 보완과 미완료 P0 분리

사용자가 수정 후 다음 작업도 계속 진행하고 테스트는 한 번에 하기를 요청했다.
앞 절의 v7·60k/50k·hard-stop 반력 복원 이후 남아 있던 180km/h 전타각 yaw 반전을
틱 단위로 조사했다. 아래는 물리 하위 작업의 기록이며 NPC/UE 통합 인수와 구분한다.

### 원인 분리

- `vehicle_cornering_probe --yaw-transient` 추가: 실제 페달로 최고속50m/s에 도달한
  다음 4초 전타각. 60/120/240Hz × Drive-full/Drive-coast/Neutral × 좌우 총18조건.
  pose·yaw·속도 주입 없이 무한 평지에서 실행한다.
- body-Z 각속도를 pitch/roll로 navigation yaw rate에 변환하고 각 타이어
  Fx/Fy·slip·Fz·spring/stop·yaw moment·횡방향 slip power·에너지를 매 틱 기록했다.
- 기존 60Hz 왼쪽 전타각 Drive-full 1.5초의 앞축 모멘트는 약+6,790Nm,
  뒤축은−8,487Nm, 합계−1,697Nm였다. 큰 조향각에서 앞타이어 횡력의 후방 성분과
  좌우 하중 차이가 만드는 `−y*Fx` 항도 중요하다. 뒤 타이어가 포화에서 풀리면서
  1.9초에는 합계약+2,609Nm로 바뀌어 yaw가 다시 입력 방향으로 증가한다.
- `Izz*Δnav_yaw/dt`와 실제 타이어 `Σ(r×F)` 차이는 최대약0.084Nm,
  모든 횡력 slip power는 음수였다. 좌우 부호/숨은 조향 cap 오류와 분리했다.
  시간 간격을 줄여도 반전이 남아 순수 60Hz 수치 발산이라고 단정할 수도 없다.

### 수정·회귀

기존 명시적 Euler는 힘0의 회전좌표 변환만으로도
`|v_next|²=|v|²*(1+(r*dt)²)`의 가짜 에너지를 만든다. 샘플링된 힘과 yaw rate를
한 step 고정하는 기존 1차 근사에서 회전좌표 항을 sin/cos로 정확 적분하도록 수정했다.
작은 각도 sinc/cosc 급수도 포함했다. 이는 전체 ODE의 정확해를 뜻하지 않는다.

- 힘/μ/terrain multiplier/마찰원/traction control/조향각/Ackermann/yaw 모멘트는
  그대로다. v7·앞60k/뒤50k 고정 강성·실제 hard-stop 반력도 유지한다.
  하중 비례 강성 실험은 다시 넣지 않았고 가짜 yaw나 부호 clamp도 추가하지 않았다.
- 새 에너지 회귀에서 기존 Euler 코드를 잠시 비교 빌드하여 FAIL을 확인한 뒤
  수정 코드를 복구했다. 기존 잔차 절댓값1.279386J>기준1J, 수정 후 최대0.100139J.
  동일 회귀의 기존 힘0 Euler 오차 식은 최대115.955J/tick이며, 전체 차량의 실제
  에너지 증가를 측정한 값과 혼동하지 않는다.
- 기존 90/180km/h × 세 페달 모드 × 좌우12개 시험에 매 틱
  `|Izz*Δnav_yaw/dt−Σ(r×F)|<0.5Nm`, `Fy*v_lateral_patch≤0.1W`를 추가했다.
- 개별 물리·설정 Release 테스트 전체 PASS, 기존 Landscape 포함 기준 완화 없음.
  도시/포화 probe189개·441행 및 신규 틱별18조건 PASS. 이 단계에서 전체 통합
  CTest나 UE 결과를 새로 합격 처리하지 않는다. 통합 빌드는 루트 작업에서 별도 수행한다.

### 효과와 남은 P0

180km/h·왼쪽 전타각·Drive-full에서 최소 navigation yaw rate는
60/120/240Hz 순으로 기존−13.739/−11.889/−10.102°/s,
수정−13.716/−11.878/−10.098°/s다. 4초 중 음수 yaw만 적분한 역방향 회전량은
기존−5.644/−4.243/−3.268°, 수정−5.613/−4.233/−3.273°다.
수치 에너지 오류는 수정했지만 반전 자체의 개선은 작다. **최고속 전타각의
고슬립 과도응답 타당성 검증은 P0 잔여**로 유지한다.

현상은 현재 포화 타이어·하중 모델의 힘과 일치한다. 그러나 이것이 실차에서도
같은 역방향 회전을 보인다는 증거는 아니다. 앞축 포화·뒤축 선형 축약 모델의
감쇠 진동 가능성만으로 현재의 뒤축까지 포화한 반전을 정당화하지 않는다.
특정 실차 데이터 동정·시간 간격 수렴·극한 조작감 인수는 미완료다.

이번 물리 하위 작업은 PID8520·9000 서버, 맵/Bake/차량 에셋을 건드리지 않았다.
사용자 PIE 테스트는 후속 작업 통합 뒤 한 번에 진행하는 요청을 유지한다.
상세 설명과 재현 명령은 [주행 보완 문서](../vehicle_driving_refinement.md)의
"2026-08-31 최고속 과도 추가 진단 — 이번 턴 후속" 절에 추가했다.

`runtime_logs/yaw-transient-20260831-exact-frame.csv`,
`runtime_logs/cornering-probe-20260831-exact-frame.csv`.

## 후속: NPC 1대의 차선·신호·장애물 주행 통합

### 요청과 구현 범위

사용자가 "수정했으면 다음 작업 진행, 테스트는 한 번에"를 요청했다. 최고속 과도응답의
남은 P0를 앞 절에 분리해 기록하고, 다음 일정의 NPC 1대 주행 기반을 선행했다.
NPC 3~4대·보행자·센서/기록을 모두 구현했다고 보고하지 않는다.

- `NpcLaneFollower`: 3D route 거리·유한 가감속·다가오는 lane 속도 제한·신호 정지선
  여유·녹색 통과 commitment·terminal/closed loop·지면 소실/큰 dt 방어.
- `SimulationHost`: route 260→270→280→290→200→210→220→230→240→250,
  시작 offset96m/ENU(20,0), ID1001, 최고6m/s. 0.25m 전방 OBB 표본으로 Ego/static/
  runtime 장애물 정지, tick-start proxy/accepted-end WorldState 일치.
- reset 이전·lease SafeStop·hard timeout·EStop 정지, 새 Play reset·동일 Play 재연결
  보존, map mismatch 제거·matching traffic 적용 후 재생성, spawn overlap 보류.
- 선택 runtime cfg/CLI 추가. 기존 cfg는 NPC off로 호환, 가상 도심 cfg만 on.
  legacy demo와 동시 사용 거부, NPC ID/proxy/255-entity 예산은 생성과 reload 양쪽 검증.
- Unreal NPC는 자체 세단+네 바퀴를 원래 scale1·270cm 축간거리로 사용한다.
  wire OBB는 ground+.85m, 시각 타이어 바닥은 ground에 정렬한다.
  매 tick 50ms bounded extrapolation·차속 기반 회전, Health 비활성에서 예측/회전 금지,
  100ms local stale/reset/연결 종료/ID 삭제 시 transient actor 정리. NoCollision 유지.

NPC는 ground 높이/yaw 기반 **kinematic proxy**다. Ego 타이어/서스펜션 동역학 복제,
NPC physical pitch/roll, 상호 질량을 고려한 양방향 충돌/전복은 구현하지 않았다.
선행 차량 가드는 표본 검사이며 복잡한 교차로 협상/추월/차선 변경이 아니다.
높은 속도/큰 맵으로 확장할 때 전방 query 예산·static spatial index 재사용을 검토한다.
