# 2026-09-01 작업일지 — 속도 단위 계측과 연석 등판 보완

## 이번 기록의 범위

먼저 사용자가 읽는 속도 단위를 명확히 하고, `50`을 **50km/h**와 **50m/s**로 각각
해석했을 때의 최대 조향 과도응답을 같은 조건으로 계측했다. 이 HUD·step-turn 작업
자체는 production 차량 물리를 바꾸지 않았으며 아래 수치는 기존 v7 solver의 관측값이다.

그 뒤 사용자 주행에서 고속으로 접근해도 연석을 오르지 못하는 문제를 별도로 수정했다.
이 후속은 Unreal 맵의 지면 저작과 C++ collision/차량 물리를 실제로 변경했다. 두 작업을
“production 물리 불변”이라는 하나의 결과로 합치지 않는다.

## HUD 단위 계약

- 기존 HUD의 `state 50 Hz` 또는 현재의 `network state rate=50.0 Hz`는 차량 속도가
  아니라 Unreal이 받은 서버 `WorldState`의 **네트워크 상태 수신률**이다.
- 새 `vehicle` 행은 승인된 최신 차량 상태의 signed body-X 종방향 속도를
  `speed=... km/h (... m/s)`로 함께 표시한다. ENU CG 궤적 속도와는 구분한다.
- 같은 행의 `gear`는 `D/N/R`, `steering`은 정규화 입력이나 개별 앞바퀴 각도가 아닌
  실제 중앙 rack 각도 `deg`, `yaw`는 서버 yaw rate `deg/s`다.
- 연결·Hello/map/play·sequence·freshness/Health gate를 통과하지 못한 상태는 마지막 값을
  계기값처럼 남기지 않고 `--`로 표시한다.

따라서 차량 설정의 `50m/s` 최대 전진 속도는 **180km/h**이고, 사용자가 말하는
**50km/h는 13.89m/s**다. 아래의 “90°”는 steering wheel/rack 각도가 아니라 probe가
실제 ENU 진행 방향 변화를 적분해 구한 차체 heading 변화다.

## 50km/h와 50m/s full-lock step-turn

`vehicle_cornering_probe`가 public throttle로 목표 속도까지 가속한 뒤 throttle `1`을
유지하면서 조향 입력 `+1`을 step으로 인가했다. brake는 `0`이며 pose·속도·yaw·brake·
steering 상태를 직접 주입하지 않았다. 60/120/240Hz에서 같은 절차를 반복했다.

| 해석한 목표 | 진입 속도 | 중앙 rack 전타 도달 | heading 90° 도달 | 90° 시 종방향 속도 | 90°까지 유효 반경 |
|---|---:|---:|---:|---:|---:|
| 50km/h = 13.89m/s | 50.01~50.16km/h | 0.342~0.350초 | 2.400~2.421초 | 32.27~32.38km/h | 18.09~18.27m |
| 50m/s = 180km/h | 180.00km/h | 0.342~0.350초 | 6.950~7.013초 | 92.26~93.19km/h | 165.85~169.11m |

즉 50km/h에서는 약 **0.34초**에 전타가 되고 약 **2.4초**에 heading이 90° 변했다.
50m/s에서는 전타 도달 시간은 같지만 90°에는 약 **7초**가 걸렸다. 둘 다 선회 중
크게 감속했으므로 이 수치는 정속 원선회 반경이나 특정 실차 정확도 검증이 아니다.

35° 조향의 순수 기하 CG 반경 약 4.13m를 50km/h로 유지하려면 약 **4.76g**가 필요하다.
현재 계측 횡한계는 약 **0.9975g**이고 앞축이 이미 `mu*Fz` 한도에 도달해, 같은 속도의
정속 최소 반경은 약 **19.7m**가 물리적인 기준이다. 60Hz probe의 첫 1초 반경은
약 **20.43m**, 감속이 누적된 90° 전체 유효 반경은 **18.09m**였다. 따라서 작은 코너는
전타각만으로 해결하지 않고 먼저 감속해야 한다. 현 모델의 거친 진입 가이드는 반경 8m
코너 약 **33km/h**, 5m 코너 약 **26km/h**이며, 노면·전이 구간·사용자 조작감에 대한
보장이나 합격 기준은 아니다.

## 연석을 벽처럼만 처리한 원인

가상 도심의 높이 0.24m·폭 0.30m 연석은 `Curb` static OBB였지만 이전
`VirtualCityGround` 59개 component에는 포함되지 않았다. 2.5m 보도도 시각 geometry일
뿐 Ground Bake 대상이 아니었다. 따라서 planar 차체 collision은 연석을 막았지만 휠 ray가
연석 뒤의 높은 지지면을 순서대로 읽을 수 없었다. 속도나 구동력이 충분해도 서스펜션이
차체를 들어 올릴 입력 지면이 없었던 것이 원인이다.

임의 속도 이상에서 차체 Z를 올리거나 모든 `Curb` 충돌을 무시하는 방식은 사용하지 않았다.
전자는 순간이동과 tick 의존성을 만들고, 후자는 지면이 없거나 잘못 저작된 연석도 관통하게
하기 때문이다.

## 저작 지면과 서버 물리 보완

- 기존 Ground 59개에 보도 116개와 연석 top 215개를 추가해 총 **390개**를
  `VirtualCityGround`에서 측정한다. 총 도형 594개와 static collider **228개**는 유지한다.
- 연석은 휠이 읽는 Ground support이면서 차체 장애물 의미를 보존하는 `Curb` marker다.
- 서버는 current→predicted pose의 swept body footprint와 겹칠 수 있는 `Curb`만 후보로
  잡는다. 유한 연석의 실제 접근 구간을 타이어 반지름 `R` 이하 간격으로 나누고 각 위치에서
  near/far 네 지점을 측정한다. near pair는 `half-width+1R`, far pair는 `half-width+3R`다.
  모든 support가 유효하고, near 높이차 절댓값이 `[0.02m, 0.75R]`, far 높이차의 부호가
  near와 같으며 `|collider 높이 - |far 높이차|| <= 0.30R`, collider 높이가 `0.75R` 이하일
  때만 해당 연석을 planar 차체 solve에서 제외한다.
- 휠 ray·spring/damper·hard-stop·타이어 힘은 그대로 Ground support를 읽어 앞축과 뒤축을
  각각 올린다. 이 경로는 차체 Z·yaw·속도나 충격량을 직접 주입하지 않는다.
- `Wall`·`Barrier`, support 누락, 0.75R를 넘는 턱은 같은 예외를 사용할 수 없으며 계속
  fail-closed한다.

저장 맵은 일반 재생성으로 덮어쓰지 않고 `BuildVirtualCity -SyncGeneratedGround`의
curb/sidewalk 전용 이행을 거쳐 **50cm** 간격으로 다시 Bake했다. 옛 1m package에 당시
absolute marker-top 후보 계약을 적용하면 경사·코너 민감성으로 164/215만 승인됐다.
50cm 재Bake와 signed-delta 계약을 함께 적용한 최종 조합은 marker 중심 214/215다. 옛
1m bytes에 최종 계약을 재감사하지 않아 개선분을 해상도에만 귀속하지 않는다.
새 collision checksum에 맞춰 기존 traffic JSON은
`ExportVirtualCityTraffic -UpdateExisting -nowrite`로 명시적으로 갱신했다.

실제 `virtual_city_v1` payload를 읽는 연석 회귀는 접근 속도 **5.2252m/s**, near support
rise **0.0736m**, 앞·뒤 차축 support 차이 **0.1600m**, 관측 차체 상승 **0.1497m**,
한 step 최대 수직 이동 **0.0232m**, 최대 pitch **3.8569°**, 최소 접지 **3개**로 연석
통과를 확인했다. 별도 synthetic 회귀에서는 0.24m support를 300N 설정으로 넘지 못했다.
20초 뒤 차체
N=3.5096m, 앞축 N=4.8596m, 속도 0.0555m/s에서 stall해 실제 ramp까지 도달한 저구동
계약을 확인했다. 6,000N 설정은 앞축→뒤축 순서로 넘으며, 60/120/240Hz crossing time
차이가 0.12초 이내였다. 별도 30/50m/s `swept-curb-stress`는 current 위치만 보던 후보 gate의 고속 tick 누락과
velocity erasure 방지 회귀다.
support가 있는 0.24m Curb는 첫 swept tick에서 각각 Δz 0.1153/0.1901m, pitch 약 5.2°, 접지 4개,
최종 Z 0.7888m를 기록했고 같은 tick의 0.30m 턱과 0.24m `Wall`은 차단됐다. 이는
**180km/h 연석 통과가 실차처럼 부드럽다는 주장이나 PIE 합격 기준이 아니다.**

- Windows C++ CTest **18/18** 성공.
- Unreal 5.6 **Game/Editor Development 빌드 성공**.
- UE Automation **29/29 성공**.
- `BuildVirtualCity -ValidateOnly`와 `ExportVirtualCityTraffic -ValidateOnly -nowrite`
  모두 성공.

50cm heightfield에서 각 authored marker 중심을 가로지르는 production full-footprint를
검사한 결과 도로와 보도를 잇는 연석 중심 214곳은 위 swept near/far 계약을 만족했다.
이는 각 collider의 **중심점 검사**이며
연석 전체 길이의 모든 접근 위치를 보장하지 않는다. endpoint나 교차로 opening처럼 raised
support가 없는 위치는 fail-closed로 막히는 것이 의도다. `Curb_BayEnd` 중심은 signed
near/far delta의 지속 raised-support 계약을 만족하지 않고 `Barrier_BayEnd`가 있는
정차 공간 끝이므로 의도적으로 eligible하지 않다. 저작된 215개 연석을 모두 통과 가능하다고
간주하지 않는다.

50cm package의 전체 along-length QA에서는 215개 중 **210개 collider 전 길이**가 계약을
만족했다. 나머지는 의도된 gap뿐이다. `Curb_BayEnd`는 전구간 `[-5,5]`이 차단되고, 북쪽
T-opening의 네 marker는 opening 쪽 끝단만 차단된다:
`Curb_North_-1_-1` `[+33.72,35]`, `Curb_North_-1_1` `[-35,-33.72]`,
`Curb_North_1_-1` `[+34.04,35]`, `Curb_North_1_1` `[-35,-33.72]`.
East grade·corner·South 연석은 전구간 eligible했다. 영구 회귀는 네 opening 쪽 endpoint의
fail-closed와 각 반대 endpoint·중심의 pass, South uniform 구간을 고정한다. 이 전체 sweep
수치는 one-off package QA 근거로 남긴다.

이 결과는 실제 저장 package를 사용한 자동 물리 회귀와 저작 데이터 검증이다. 사용자가
직접 조작하는 PIE에서 진입 속도·각도에 따른 체감, 화면의 앞축→뒤축 움직임, 보도 위 안정,
벽·Barrier 비관통은 아직 수동 인수 전이다. 자동 결과만으로 PIE 인수를 완료 처리하지 않는다.
원인·재Bake·진단 순서는 [연석 등판 해결 사례](../troubleshooting/virtual-city-curb-climb-ground-support.md)를 따른다.

## 계기판·배기가스·엔진/타이어음 선행 구현

사용자 요청에 따라 Unreal presentation layer에 외부 에셋과 Blueprint 수동 설정이 없는
세 기능을 추가했다.

- 기본 GameMode가 `ASimCoreInstrumentClusterHud`를 자동 설치한다. authoritative 속도(km/h),
  RPM, 기어, 연료를 표시하고 stale/reconnect/offline에서는 이전 값을 지운다. 주차 브레이크는
  서버 확인 필드가 없어 로컬 command intent로만 표시한다.
- `USimCoreExhaustComponent`는 RPM·종가속도로 runtime CPU sprite 배출량을 만들며 stale이면
  0으로 감쇠한다.
- `USimCoreVehicleAudioComponent`는 RPM 기반 엔진 tone과 차속·접지·published slip 기반
  타이어 noise를 합성하며 stale이면 무음 처리한다.
- 세 경로 모두 `WorldState`를 읽는 표시 기능이고 C++ SimCore 물리·제어로 값을 되먹이지 않는다.

UE 5.6 Editor 통합 빌드가 성공했고 focused Automation은 계기판 **2/2**, 배기가스 **2/2**,
오디오 **1/1** 성공했다. 로그는 각각
`runtime_logs/ue-instrument-cluster-automation-20260901.log`,
`runtime_logs/ue-exhaust-automation-20260901.log`,
`runtime_logs/ue-vehicle-audio-automation-20260901.log`다.

실제 PIE에서 16:9 가독성, 카메라/기존 diagnostics HUD와의 겹침, 배기 위치·농도, 엔진음
음정·음량, 속도/slip별 마찰음과 End PIE/reconnect 전환은 아직 수동 인수 전이다.
