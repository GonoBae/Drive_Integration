## 문서에서 사용하는 말

설명에는 쉬운 이름을 먼저 쓰고, 코드를 찾는 데 필요한 이름을 함께 적습니다.
영어로 옮길 때도 한 문장에는 한 가지 내용을 담습니다. 아래 영어는 설명용 표현이며 코드 이름을 바꾸지는 않습니다.

| 코드·기술 용어 | 쉬운 설명 | 영어로 설명할 때 |
|---|---|---|
| `MapPackage` | 서버용 맵 데이터 | Server map data |
| Bake / Export | 맵 정보를 측정해 파일로 저장 | Export map data |
| `WorldState` | 서버가 계산해 보낸 차량·교통 상태 | Simulation state |
| tick | 시뮬레이션 계산 한 번 | Simulation step |
| snapshot | 특정 시점의 상태 | State at a specific time |
| loadout | 차량 부품 조합 | Vehicle setup |
| 상태 신선도 | 마지막 상태를 받은 뒤 지난 시간 | Time since the last state was received |
| 인수 | 정한 완료 기준을 실제로 확인하는 단계 | Final validation |

초당 계산 횟수(Hz), 길이·무게 단위와 제한 조건은 생략하지 않습니다. 미구현 기능을 현재 기능처럼
간단히 줄이지 않으며, 명령어·파일 경로·메시지 필드 이름은 그대로 유지합니다.

## README 언어 구성

공개 소개는 **영어 기본판과 별도 한국어판**으로 제공합니다. 두 판의 기능·실행법·제약은 동일하게 관리합니다.
한 문서에서 문단마다 두 언어를 반복하지 않습니다. 상세 기술 문서는 당분간 한국어로 유지합니다.

| 파일 | 역할과 관리 범위 |
|---|---|
| `README.md` | 영어 기본 소개. 짧은 문장, 실제 화면과 핵심 구조, 현재 기능, Windows 실행/조작법, 제약, 상세 문서 링크 |
| `README.ko.md` | 같은 순서·같은 기능 범위의 한국어판. 국내 지원 시 직접 공유 가능 |
| `docs/README.md` 이하 | 상세 기술 문서는 당분간 한국어 유지. 영어 README에서 연결할 때 한국어 문서임을 표시하고, 핵심 설계 설명만 필요에 따라 번역 |
| `docs/images/` | 실제 화면과 개념도 원본 공유. 공용 그림의 핵심 표기는 쉬운 영어로, 두 언어의 캡션에서 설명 |

두 README 상단에는 `English | 한국어` 링크를 둡니다. 채용 담당자가 읽는 순서에 맞춰
프로젝트 소개 → 직접 구현한 부분 → 구조와 실행 방법 → 문제 해결과 검증의 네 항목으로 구성합니다.
소개에는 현재 동작 범위와 한계를, 구현 설명에는 목적과 데이터 흐름을 적습니다.
문제 해결은 증상·수정·확인 방법을 연결하고, 검사 날짜와 실제 화면 확인 여부를 구분합니다.
세부 기능·실험 옵션·테스트 이력은 README에 반복하지 않고 기존 문서로 연결합니다.
개발 배경은 본인이 확인한 회사 업무(패킷 송수신·직렬화, 전체 소프트웨어 구조 설계)와
이번 개인 프로젝트에서 추가한 디버그 화면을 구분합니다. 프로젝트 통신 규격이 회사의 규격과 같다고 주장하지 않습니다.
대표 화면/영상은 실제 실행에서 촬영한 원본을 사용하고 촬영일·실행 조건을 함께 적습니다.
화면 촬영을 전체 주행 인수나 성능 측정으로 간주하지 않으며, 개념도를 실행 화면으로 소개하지 않습니다.
세부 테스트 이력과 긴 물리 설명은 옮겨 적지 않고 기존 문서로 연결합니다. 완료하지 않은 전환은 현재 기능에 섞지 않습니다.

영어판을 공개 설명의 기준으로 관리하고, 기능·명령어·제약이 바뀌면 한국어판도 같은 변경에서 수정합니다.
기술 사실은 코드와 `status.md`의 검증 기록을 따릅니다. 이미지 원본은 복제하지 않고 언어별 설명만 달리합니다.
명령어·버전·키·경로는 번역하지 않으며, 긴 전문 용어보다 일반적인 짧은 문장을 사용합니다.
GitHub의 README 노출과 상대 링크 규칙은 [공식 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)를 따릅니다.

## 주기적으로 관리할 문서

매일 모든 파일을 고치는 대신 **주간 점검 + 관련 변경이 생길 때 갱신**합니다.
결과는 한곳에 기록하고 다른 문서는 링크로 연결합니다.

| 문서 | 갱신 시점 | 관리할 내용 |
|---|---|---|
| `status.md` | 작업·검사 종료 후, 주간 점검 | 구현/미구현, 실제 검사 날짜·결과·로그, 다음 우선순위 |
| `architecture.md` | 책임·통신·계산·데이터 계약 변경 시 | 현재 구조, 선택 이유, 제약과 미구현 범위 |
| `guides/core_validation.md` | 검사·측정 방법 변경 전후 | 실행 방법, 지표 정의, 비교 조건·완료 기준. 결과 원장은 `status.md` |
| 루트 `README.md`·`README.ko.md` | 사용법·공개 기능·제약 변경 시 | 같은 범위의 영어/한국어 소개와 조작법 |
| 나머지 `guides/`·`reference/` | 해당 기능 변경 시 | 맵·NPC·신호·충돌·입력 측정·배포의 실제 절차와 조건 |
| `assets/README.md`·에셋 출처 파일 | 에셋 반입·수정·배포 검토 시 | 원본 출처, 변경 이력, 확인 당시 배포 조건과 증빙 |

외부 연구 계획은 개인 학습 폴더에서, 교재 원본은 아래 보관 폴더에서 관리합니다.
이전 교재·일일 기록은 매번 고치지 않습니다. 현재 설명과 다르면 저장소 문서를 우선합니다.
연구 제안에는 `계획`, 실제 측정에는 실행 조건과 근거를 남기고 자동 검사로 화면·청감 인수를 대신하지 않습니다.

## 이전 자료

교재와 과거 문서는 아래 프로젝트 외부 폴더에 보관했습니다.

```text
B:\Portfolio\Drive_Integration_Archive\2026-09-19-18ccd877\
├── study\                 교재·면접 PPT·자동 테스트 교재
├── docs_before_cleanup\   이번 정리 전 문서 원본 51개
│   ├── worklogs\          날짜별 작업·검증 기록
│   ├── decisions\         기술 결정의 원래 검토 내용
│   └── troubleshooting\   상세 문제 해결 사례
├── archive\               이전 로그·제작 중간 자료·배포 후보·정리 백업
└── project_cleanup\       과거 비교 실험·Unreal 테스트/패키징 결과
```

일정표·기능표·긴 변경 이력은 현재 상태와 설계 설명으로 요약했습니다. 원본51개는
복사 전후 SHA-256을 비교해 보관했으므로 복구할 수 있습니다. 원본의 상대 경로는
정리 당시 구조를 기준으로 합니다. 현재 실행 절차는 위 문서 목록을 따릅니다.

외부 보관본은 **현재 PC에만 있으며 Git에는 포함되지 않습니다.** 기존에 커밋한 문서는
Git 이력에서도 확인할 수 있습니다. 과거 기록의 `runtime_logs/…`는 위 `archive/` 아래
동일한 상대 경로에서 찾습니다. 새 실행 로그는 프로젝트에 다시 생성됩니다.

코드·테스트·지도·에셋과 필요한 개발 도구는 유지합니다. 이전 지도와 재질도 회귀 시험
또는 현재 맵에서 사용하므로 보존합니다. 에셋 출처와 배포 조건은 프로젝트에 계속 남깁니다.

`project_cleanup/`는 원래 프로젝트 상대 경로를 보존합니다. Chrono 비교 실험 원본과
Unreal의 이전 자동 검사·백업·Cook·Stage·크래시 자료는 이곳에서 찾을 수 있습니다.
현재 실행 파일과 의존성·빌드 캐시, 사용자 자동 저장본·주행 기록·스크린샷·개인 설정은
프로젝트에 남깁니다. 실행·빌드 중인 프로세스가 사용하는 영역은 정리하지 않습니다.
